# Requisitos del sistema revisados — v2

Esta versión revisa los [requisitos iniciales v1](../requisitos-v1.md) a partir de la evaluación general registrada en [evaluación y decisiones](evaluacion-y-decisiones.md) y del [contexto y alcance](../contexto-y-alcance.md). La v1 se conserva como evidencia de la versión inicial. El contexto no se ha reescrito: si una frase suya sigue en tensión con esta versión, se indica aquí y en el registro de decisiones.

El sistema es el Sistema de Generación Automática de Modelos y Pruebas de Ciberseguridad mediante IA Generativa. El analista lo utiliza desde la interfaz web ya descrita en el contexto. El flujo es: ingesta y confirmación de etiquetas, generación del modelo, confirmación del modelo, generación de casos en estado Pendiente, validación estática y, solo después, ejecución del subconjunto seleccionado contra la API de simulación o de referencia.

Estas elecciones cierran las observaciones E5-001 a E5-037. Siguen fuera del alcance el reentrenamiento del LLM, la corrección del código de la API, las pruebas destructivas o no autorizadas sobre producción, la conversión del modelo en políticas ejecutables de un motor externo y la auditoría física de la red. Esta versión no fija una revisión de NIST SP 800-53, un contrato HTTP, un formato de archivo para las pruebas o el baseline, reconocimiento de texto en imágenes ni un umbral distinto de los ya escritos.

### Validación de artefactos

| ID | Requisito | Descripción | Módulo | Cómo comprobarlo |
| --- | --- | --- | --- | --- |
| GMP-RF-008 | El sistema deberá validar, sin ejecutar pruebas ni llamar a la API, la consistencia sintáctica, semántica y lógica del modelo y de los casos respecto de los requisitos. | Es un Error sintáctico la falta de un campo obligatorio del modelo o del caso. Es un Error semántico la referencia a un rol, recurso, acción o permiso que no existe en el modelo. Es un Error lógico una contradicción entre reglas, un permiso huérfano o un rol sin permisos. | Validación | Provocar por separado un campo obligatorio vacío, un caso con un permiso inexistente y dos reglas contradictorias. Comprobar que cada caso se clasifica como Error y que no se envía ninguna petición HTTP. |
| GMP-RF-009 | El sistema deberá emitir el informe de validación estática antes de cualquier petición a la API y clasificar cada incidencia como Error o Advertencia. | Los hallazgos de GMP-RF-008 son Error e impiden iniciar la ejecución. Es Advertencia que un requisito de ciberseguridad segmentado no tenga ningún caso; la Advertencia se muestra y no impide la ejecución. No se añade otro umbral de cobertura. | Validación | Con una contradicción, comprobar que el informe muestra Error y que la orden de ejecución no envía peticiones. Con todos los requisitos cubiertos por casos y sin Error, comprobar que no hay advertencia de cobertura y que la ejecución puede solicitarse. ### Ejecución de pruebas

| ID | Requisito | Descripción | Módulo | Cómo comprobarlo |
| --- | --- | --- | --- | --- |
| GMP-RF-010 | El sistema deberá permitir al analista seleccionar un subconjunto de casos, de uno en uno o mediante filtros, para ejecutarlo. | Los filtros son el requisito de origen, el tipo autorizado o denegado y, si ya hay informe de validación, la severidad Error o Advertencia de las incidencias asociadas al caso. No existe otra selección hecha por el sistema sin esa indicación del analista. | Ejecución | En un conjunto de 10 casos sin Error, seleccionar 3 y comprobar que la ejecución solo los incluye. Filtrar por un requisito y por el tipo denegado, y comprobar que el subconjunto coincide. Sin informe de validación, comprobar que el filtro de severidad no selecciona casos. |
| GMP-RF-011 | El sistema deberá ejecutar solo el subconjunto seleccionado contra la API de simulación o de referencia indicada por el analista, registrar el código de estado y el payload, y asignar Pass, Fail o Error. | El destino no es un entorno de producción. Este requisito no fija la ruta, el método ni el esquema del cuerpo: la petición transporta el sujeto o rol, el recurso, la acción y los datos de entrada. Pass significa que el código recibido es el que el caso asocia a su resultado esperado; en un caso de denegación de la comprobación, 403 Forbidden es Pass. Fail significa que se recibió otro código. Error significa que la API no responde o se produce un error de red no controlado. El payload queda registrado y no cambia por sí solo el veredicto. | Ejecución | Indicar la API simulada. Ejecutar una denegación que recibe 403 y comprobar Pass y el registro del payload. Repetir la denegación con otro código recibido y comprobar Fail. Impedir la respuesta de la API y comprobar Error. Comprobar que el destino utilizado es la API de simulación o de referencia. |

| GMP-RF-012 | El sistema deberá mantener un enlace bidireccional entre cada caso, un único requisito de ciberseguridad de origen y una única regla del modelo lógico. | El elemento del modelo enlazado es la regla. Desde el caso, el requisito o la regla se consultan los otros dos. ## 3. Lecturas que el contexto aún no recoge

Estas tres frases del contexto no se han modificado. Los requisitos de esta versión usan la lectura indicada:

- La validación previa se resuelve en GMP-RF-009: un Error impide la ejecución y una Advertencia no la impide. El supuesto que dice que el sistema «puede advertir» ante fallos críticos no distingue esas severidades.
- La cobertura absoluta de GMP-RF-013 no usa el baseline. El baseline se usa en GMP-RF-014 y GMP-RNF-004. El supuesto que atribuye también la cobertura a la verdad de referencia del baseline queda más amplio que estos requisitos.
- «Modelo lógico verificado», en la función de generación de pruebas del contexto, se lee aquí como modelo confirmado por el analista. La validación estática es posterior a la generación de los casos.
